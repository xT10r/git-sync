# План доработки Git-Sync

Дата: 2026-10-14. Статус: базовая реализация поставщика снимков подготовлена в feature/git-sync-reliability; проверяется перед выпуском.

База: `main`, коммит `57fa43e1708c7fd73f5c9c7a968bdd4454abf673`.
Ветка: `feature/git-sync-reliability`. Изменения из `develop` не включены.

## Выполнено в текущей ветке

- Исправлена исходная тестовая база; затем заменена проверками нового единственного пути исполнения.
- Реализованы typed config, отдельный worker/HTTP, Git cache, подготовка снимков по SHA, atomic current, last-good, root lock и restart recovery.
- Удалены прежние Pull/reset pipeline и незавершённые api/daemon, globals и ненужные зависимости.
- Обновлены Go/dependencies, Dockerfile и CI/release; исправлены обе версии README и описана несовместимая миграция.
- Добавлены локальные Git/HTTP fixtures, force-push/новый SHA/reader consistency/failure/auth/recovery тесты и subprocess SIGTERM.

Ограничения этой поставки: готовые snapshots сохраняются без автоматической очистки; backoff/jitter, SSH/LFS/submodules/symlinks, Windows runtime и гарантии NFS не реализованы. Windows только кросс-компилируется. Docker/Kubernetes runtime надо проверить в среде с container engine. Подробные фактические результаты — [verification.ru.md](verification.ru.md). Дальнейшие пункты ниже описывают целевой объём; наличие пункта не означает, что все его подпункты уже выполнены.

## Основание плана

Подготовлен [архитектурный анализ](architecture-review.ru.md). Владелец подтвердил контракт поставщика неизменяемых снимков 14 октября 2026 года. Для поставки связанных конфигурационных файлов публикация снимков и сохранение last-good входят в основные требования. Архитектурный анализ уточняет статические находки, ограничения тестов и целевую структуру.

## Цель и границы

Обеспечить поставку неизменяемых снимков выбранной удалённой Git-ревизии для контейнеров и Kubernetes sidecar. Сервис владеет root/cache/snapshots; изменяемые данные потребителя располагаются отдельно. Каждый снимок привязан к SHA, готовится отдельно и публикуется после успеха. При сбое сохраняется last-good. Поддержка редактируемой рабочей копии не входит в целевой продукт; старый local-path требует миграции.

Документ основан на чтении исходников main. Ниже разделены обнаруженные дефекты и предлагаемые улучшения. Сборка, тесты и измерение покрытия в рамках подготовки документа не выполнялись. Успешные старые запуски CI не заменяют проверку нового изменения.

## Правила веток и изменений

Применяется соглашение, указанное владельцем репозитория: `feature/<functional-name>` для развития функциональности, `hotfix/<fix-name>` для срочного исправления и `refactor/<functional-name>` для рефакторинга. Имя ветки описывает функциональность, а не тип первого файла или коммита.

Текущая ветка `feature/git-sync-reliability` предназначена для повышения надёжности синхронизации и содержит план как первый результат работы. Тесты и документация входят в соответствующие функциональные изменения. Новые ветки создавать от актуального main; содержимое develop исследовать отдельно и переносить только после проверки конкретных изменений. Каждый этап оформлять небольшим проверяемым изменением с регрессионными тестами.

## Последовательность работ

### 1. Воспроизводимая тестовая база — refactor/offline-git-fixtures

- Создать локальные bare remote и рабочие копии через t.TempDir(); добавить helpers для коммитов, нескольких веток и переписывания истории.
- Заменить интернет-зависимые проверки на локальные fixtures. Для HTTP и auth использовать httptest и контролируемый Git HTTP endpoint.
- Изолировать env через t.Setenv, webhook-каналы, HTTP mux и Prometheus registry между тестами.
- Сначала зафиксировать текущее поведение; тесты дефектов добавлять вместе с исправлениями, чтобы main оставался зелёным.

Приёмка: тесты после получения Go-зависимостей выполняются без внешнего Git-сервера, повторный запуск не зависит от предыдущего.

### 2. Контракт Git-синхронизации — feature/branch-synchronization

- Явно выбирать настроенную ветку при clone и последующих обновлениях; проверять remote URL и refs существующей копии.
- Сравнивать commit SHA отдельно от diff файлов.
- Готовить отдельный снимок выбранного SHA; опубликованные снимки не менять. Изменения потребителя внутри снимка считать нарушением контракта, не переносить в следующую версию.
- Определить поведение force-push, отсутствующей/удалённой ветки и пустого remote: неуспешная подготовка сохраняет last-good.
- Не удалять untracked/ignored файлы без отдельной явно включённой политики; hard reset не считать доказательством их очистки.
- Применять общую auth-конфигурацию ко всем сетевым операциям; публичный HTTPS должен работать без credentials. SSH — отдельная задача с known_hosts, если нужен.
- Проверить путь, чужой непустой каталог, symlink и права доступа до разрушительных операций.

Приёмка: выбранная ветка с default=main и target=release синхронизируется правильно; повторный sync идемпотентен; после ошибки сохраняется понятное состояние. Тесты: fast-forward, одинаковое дерево/новый SHA, force-push, dirty tracked, untracked/ignored, отсутствующая ветка, отказ auth и некорректный remote.

### 3. Ошибки и жизненный цикл — feature/runtime-errors

- Вынести управляемую функцию запуска с возвратом ошибки; назначить ненулевой exit code при неверных параметрах и фатальных ошибках.
- Возвращать исходную ошибку Sync, сохранять причины через wrapping; не маскировать её ошибкой чтения метаданных.
- Передавать context и ограничивать время сетевых операций; останавливать и дожидаться goroutine при SIGTERM.
- Сериализовать изменение репозитория, отдавать безопасный snapshot состояния.
- Повторять временные сетевые ошибки с ограниченным backoff; ошибки конфигурации не повторять бесконечно.

Приёмка: subprocess-тесты exit code; отмена зависшей операции; ошибка sync доступна вызывающему коду; конкурентные чтения состояния проходят race detector.

### 4. HTTP, webhook и готовность — feature/http-lifecycle

- Использовать отдельные ServeMux и http.Server с таймаутами и Shutdown.
- Возвращать ошибку bind вызывающему коду.
- Ограничить webhook методом POST; неблокирующая ограниченная очередь с документированным ответом при переполнении.
- Ответ webhook означает принятие задания, а не успешное завершение sync.
- Валидировать неполную Basic-конфигурацию и конфликт Basic/Bearer; исключить credentials из логов.
- Реализовать /status, liveness и readiness: готовность после первого успешного sync; политику устаревания после сетевых ошибок описать отдельно.

Приёмка: httptest для 401, разрешённого доступа, неверного метода, полной очереди и shutdown; bind conflict возвращает ошибку; readiness меняется по состоянию синхронизации.

### 5. Конфигурация и наблюдаемость — feature/config-and-metrics

- Зафиксировать приоритет CLI > env > defaults. Поддержку конфигурационного файла либо реализовать с тестами, либо убрать неподтверждённое обещание из README.
- Унифицировать имена env в constants, Dockerfile и документации; при необходимости оставить документированные deprecated aliases.
- Валидировать путь, URL, интервал и адрес сервера; использовать net.SplitHostPort.
- Ввести duration, время последнего успеха и признак результата sync. Ограничить labels; подробности коммита отдавать через status/логи.
- Сохранить совместимость метрик либо документировать миграцию.

Приёмка: табличные тесты приоритета/ошибочных значений, IPv4/IPv6, aliases и отсутствующего пути; проверки счётчиков успеха/ошибки и ограниченного числа серий после множества коммитов.

### 6. Подготовка и публикация снимков — feature/snapshot-publication

- Разделить Git cache, snapshots/<SHA> и published pointer current в принадлежащем сервису root.
- Подготовить и проверить снимок до переключения current; status и метрики обновлять после commit-point.
- Зафиксировать путь снимка в контракте чтения нескольких файлов; потребителю предоставлять доступ для чтения.
- Сохранять last-good при отказе fetch/checkout/publish; обеспечить restart/recovery после прерванной подготовки.
- Реализовать один writer на root, retention и очистку временных объектов; не удалять снимки раньше документированного срока чтения.
- Документировать миграцию старого local-path и ограничения FS/platform.

Приёмка: отказ на каждом этапе подготовки не меняет current; SHA status соответствует снимку; reader-test читает согласованную версию; restart восстанавливает published state; второй writer отклонён; cleanup не удаляет active snapshot. Проверить одинаковое дерево/новый SHA и force-push.

### 7. Контейнер, CI и документация — feature/build-and-release

- Выбрать поддерживаемую версию Go и совместимые зависимости после проверки официальной документации и vulnerability scan.
- Убрать секреты из build ARG; применять runtime env или secret files.
- Запускать образ непривилегированным пользователем с документированными правами на volume.
- Проверить сборки Linux/Windows/macOS; ARM64 добавлять при подтверждённой потребности.
- Обновить release actions, минимальные permissions и extraction release notes; включить checksums артефактов.
- Обновить README, примеры Docker/Kubernetes и CHANGELOG по реально реализованному поведению.
- Подключить либо удалить незавершённые api/daemon заготовки после определения публичного контракта.

Приёмка: контейнерный smoke-тест clone → update → restart с тем же volume → SIGTERM; проверка auth через runtime env; сборки заявленных платформ и корректные release artifacts.

## Обязательные проверки реализации

Для каждого PR выполнять применимые проверки и указывать фактические результаты:

- gofmt: отсутствие неформатированных Go-файлов.
- go vet ./...
- go test ./...
- go test -race ./... на поддерживаемом runner.
- go test -coverprofile=coverage.out ./...; оценивать покрытие новых ветвей ошибок, а не только общий процент.
- go build ./cmd/; для изменений сборки — cross-build заявленных платформ.
- Для Docker/HTTP/lifecycle — соответствующие интеграционные и subprocess-тесты.
- Для зависимостей — govulncheck после установки совместимой версии инструмента.

Не вводить произвольный процент покрытия до измерения baseline. Каждый исправленный дефект должен иметь регрессионный тест, который воспроизводит исходную проблему. Отдельно проверять, что сообщение об успехе и счётчик успешных обновлений не появляются после отказа.

## Очерёдность и выпуск

Порядок: подтверждённый контракт поставщика снимков → тестовые fixtures → Git/ветка/auth → ошибки и shutdown → HTTP → конфигурация/метрики → публикация snapshots → измерения и оптимизация → контейнер и release. Каждый шаг можно поставлять отдельным PR; обновление toolchain допускается раньше, если необходимо для тестов.

Перед релизом сверить CLI/env/HTTP/метрики на совместимость, описать изменения поведения локальных файлов, проверить сценарий обновления с существующим volume и возможность возврата к предыдущему образу. Примеры не должны содержать реальные токены.

## Вопросы перед реализацией

1. Определить retention снимков и максимальный срок чтения потребителем.
2. Нужны ли SSH и конфигурационный файл в ближайшем релизе?
3. Уточнить поддерживаемые FS и способ публикации на каждой платформе; атомарная публикация входит в обязательные требования.
4. Какие платформы, версии Git-серверов и сценарии Kubernetes обязательны?

Эти вопросы не мешают начать изоляцию тестов и исправление передачи ошибок. Решения, затрагивающие удаление данных и совместимость, фиксировать до реализации соответствующего этапа.
