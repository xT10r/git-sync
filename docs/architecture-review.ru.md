# Архитектурный анализ Git-Sync и предложение развития

Дата: 14 октября 2026 года. Анализируемая база: main, SHA `57fa43e1708c7fd73f5c9c7a968bdd4454abf673`.
Рабочая ветка: `feature/git-sync-reliability`.

## 1. Что приложение должно делать

По docs/readme.ru.md сервис поддерживает локальную копию удалённого Git-репозитория для потребителей конфигураций, скриптов и документации. Проверка кода уточняет направление: remote → local. В приложении нет commit/push и механизма отправки локальных правок. Локальные изменения вызывают reset. Поэтому формулировка README «любые изменения ... вызывают синхронизацию» означает восстановление локальных данных, а не двустороннюю синхронизацию.

Это самостоятельный Go-сервис; связь с выгрузкой хранилища 1С/OneScript из текущего кода не следует. Его полезный результат — доступный потребителю набор файлов выбранной версии Git, а не факт вызова Pull.

Проверенные текущие механизмы:
- один remote, одна заданная ветка, один локальный каталог на процесс;
- при создании GitRepository выполняется clone/open и сохранение текущего HEAD;
- затем HTTP запускается независимо, scheduler вызывает Sync по тикеру или входящему сигналу /webhook;
- Sync делает clone/open → fetch → diff деревьев → условный pull → проверку dirty worktree → условный reset;
- метрики и логи описывают попытки и текущий коммит.

Ниже предлагается уточнённый целевой контракт. Это проектное решение, а не утверждение о неизвестных намерениях владельца:

> Сервис получает выбранную Git-ревизию и публикует проверенный локальный снимок. При успешной публикации потребитель может определить опубликованный SHA. При сетевой ошибке сохраняется последняя успешно опубликованная версия, а состояние устаревания видно в status и метриках.

Нужно различать два возможных продукта:
1. **Управляемая рабочая копия:** потребитель обращается к стабильному каталогу, допускается изменение файлов на месте и отдельно определяется судьба локальных правок.
2. **Поставщик снимков для приложения:** сервис владеет служебным каталогом, потребитель читает опубликованный неизменяемый снимок через ссылку/указатель.

README перечисляет прежде всего потребителей второго типа. Поэтому рекомендую ориентировать развитие на поставщика снимков, сохранив прежнюю рабочую копию как явно ограниченный режим совместимости. Если основная потребность — редактируемая Git-копия, приоритет атомарной публикации и контракт локальных правок потребуется пересмотреть.

## 2. Общая экспертная оценка

Текущая реализация — небольшой прототип сервиса согласования состояния. Масштаб кода позволяет исправить его без большого фреймворка, но сейчас она не обеспечивает надёжный контракт поставки файлов: решение об обновлении завязано на diff деревьев, обновление неатомарно, ошибки теряются, готовность не определена.

Сильная сторона — ограниченная задача и последовательный цикл. Основной недостаток — в модели смешаны «изменения обнаружены», «обновление выполнено» и «версия опубликована». Из этой путаницы следуют ошибки метрик, неверные сообщения об успехе и неопределённое поведение при сбоях.

Не следует сначала переносить код по новым каталогам. Вначале нужен контракт и тесты его инвариантов; иначе получится более аккуратно разложенная прежняя логика.

## 3. Плюсы текущего подхода

| Решение | Польза | Ограничение |
|---|---|---|
| Один репозиторий на процесс | Простая изоляция, удобная модель sidecar, небольшой объём состояния | Нельзя без дополнительного проектирования разделять один root между процессами |
| Последовательный scheduler | В штатном Start нет параллельных sync; меньше конфликтов Git | Публичный Sync и общие globals не защищают от альтернативного вызова |
| go-git вместо shell-команд | Нет зависимости от установленного Git, типизированные ошибки и API, удобно создавать fixtures | Это отдельная реализация Git; совместимость транспорта и операций надо проверять |
| Периодический опрос плюс входящий webhook | После потерянного сигнала следующий опрос всё равно обнаружит изменения | Это сигнал «проверь сейчас», а не очередь каждого коммита |
| Prometheus | Уже есть интеграция с эксплуатационным мониторингом | Текущий состав labels и семантика счётчиков требуют изменения |
| Context и обработка SIGTERM | Намечен управляемый жизненный цикл | Context не достигает транспорта/HTTP и завершение goroutine не ожидается |
| Несколько небольших пакетов и интерфейс Gitter | Есть начальное разделение обязанностей и тестовые подстановки | Направление зависимостей и API пока привязаны к реализации |
| Docker и CI | Есть путь доставки и автоматические проверки | Наличие pipeline не доказывает покрытие рабочих сценариев |

## 4. Архитектурные и структурные замечания

Уровни: **критично** — влияет на правильность/сохранность результата; **существенно** — влияет на устойчивость, поддержку и наблюдаемость; **структурно** — усложняет развитие, хотя само по себе не обязательно ломает работу.

### 4.1. Алгоритм и целостность результата

| № | Уровень | Факт в коде / риск | Предложение |
|---|---|---|---|
| A1 | Критично | Clone выбирает default remote HEAD, сравнение использует настроенную branch, Pull не задаёт ReferenceName. Выбираемая и обновляемая ревизии могут отличаться. | Разрешать target ref в один SHA и использовать именно его для подготовки копии. |
| A2 | Критично | Решение об обновлении — diff.Len() > 0. Разные коммиты с одинаковым деревом не обновляют HEAD/метаданные. | Изменение ревизии определять по SHA; TreeHash использовать лишь для оптимизации файловой публикации. |
| A3 | Критично | Force передаётся в Pull, но go-git v5.12.0 внутри Pull проверяет fast-forward и возвращает ErrNonFastForwardUpdate. Force не делает рабочую копию зеркалом после переписывания истории. | Для зеркального продукта готовить snapshot конкретного remote SHA; не использовать merge/pull как основной механизм согласования. |
| A4 | Критично | Pull вызывается до очистки dirty worktree. При новых remote-файлах и конфликтующей локальной правке операция может завершиться до reset. | Политику локальных данных применять до обновления; предпочтительно исключить запись потребителя в управляемые snapshots. |
| A5 | Критично | Файлы изменяются на месте, гарантий атомарной публикации нет. Потребитель может прочитать часть старой и часть новой конфигурации. | Подготовка отдельного snapshot и переключение указателя только после успеха. |
| A6 | Критично | Fetch использует сохранённый origin существующего каталога, Pull задаёт configured URL. При смене настройки сравнение и получение данных могут обращаться к разным источникам. | Проверять идентичность repo/ref/root; смену источника проводить как контролируемую миграцию. |
| A7 | Существенно | Clone/open выполняется в конструкторе; сначала выполняется сеть, затем стартует HTTP. Ошибка первой загрузки немедленно завершает процесс, нет управляемого initial retry. | Чистая конфигурация/конструктор, затем Run и начальное согласование с timeout/retry. |
| A8 | Существенно | Существующая копия до первого тика не приводится к target; клонирование может выбрать другую ветку. Initial clone также не проходит через счётчики Sync. | Один путь initial и periodic reconcile, первый вызов сразу после запуска. |
| A9 | Существенно | Нет продуктового контракта для untracked/ignored, локальных коммитов, отсутствующей ветки, пустого remote и частичного clone. | Матрица состояний с ожидаемым результатом; удаление только принадлежащих сервису объектов. |
| A10 | Существенно | Каждый цикл открывает репозиторий, строит diff деревьев и проверяет весь worktree; при изменении Pull дополнительно делает fetch. Clone не ограничен Depth/SingleBranch. | Один fetch нужного ref, сравнение SHA, пропуск дорогостоящих операций при отсутствии изменений. |
| A11 | Существенно | Два процесса могут одновременно использовать один path; mutex процесса этого не предотвращает. | Явное «один writer на root», lock с политикой отказа и отдельный root на instance. |
| A12 | Существенно | Поддержка LFS, submodules, symlinks и file mode не оговорена. Обычный checkout не равнозначен получению полного содержимого LFS/submodules. | Ограничить поддерживаемый набор; unsupported-сценарии обнаруживать и объяснять до публикации. |

Замечание к reset: комментарий обещает удаление всех untracked, но фактический контракт нельзя выводить из имени HardReset или поведения системного Git. Зафиксированная версия go-git имеет собственный алгоритм. Судьбу untracked/ignored, конфликтующих путей и symlinks проверить отдельными fixtures; не обещать очистку до этих проверок.

### 4.2. Границы пакетов и модели

| № | Уровень | Наблюдение | Предложение |
|---|---|---|---|
| S1 | Существенно | GitRepository принимает FlagSet, достаёт параметры через type assertion, выполняет IO и пишет логи. CLI проникает в инфраструктуру Git. | Типизированный RepositoryConfig; parsing/validation только на входе. Ошибки возвращать, логировать на границе операции. |
| S2 | Существенно | Gitter отдаёт Options, HasChanges, Commit отдельными вызовами. Это состояние, которое может не относиться к одной завершённой операции. | Sync(ctx) → Result + error; Result содержит SHA, Changed, PublishedAt и outcome. |
| S3 | Существенно | interfaces импортирует конкретный пакет git; Syncer использует *GitRepository, а GitSync реализует методы с Gitter, поэтому объявленный Syncer не соответствует GitSync. | Удалить неиспользуемый контракт; небольшой интерфейс определять рядом с потребителем и описывать операцию. |
| S4 | Существенно | CommitInfo содержит *object.Commit и mutable Changes. Commit отдаёт внутренний указатель после Unlock; CommitHash читает без lock/nil-check. | Snapshot значений без объектов backend; копировать mutable slices или не включать их в публичное состояние. |
| S5 | Существенно | Mutex защищает отдельные поля, но не весь Git lifecycle. Наличие mutex создаёт впечатление большей безопасности, чем обеспечивает. | Один worker владеет backend; отдельная синхронизация чтения status. Проверка -race. |
| S6 | Существенно | Scheduler напрямую импортирует handlers ради global WebhookCh и metrics ради обновления глобальных collectors. HTTP управляет каналом доменной операции. | HTTP получает Trigger-функцию сервиса; worker владеет очередью. Метрики получают завершённый Result. |
| S7 | Существенно | DefaultServeMux, registeredPaths, WebhookCh, default registry и singleton logger создают общий жизненный цикл для независимых компонентов. | Собирать объекты в main; локальный mux/registry/queue, logger передавать явно. |
| S8 | Структурно | api/ дублирует направление HTTP, daemon/ незавершён, models/ пустой, mock/ содержит только тестовые объекты. Public git/logger не имеют заявленного library API. | Внутреннюю реализацию поместить в internal; удалить пустые заготовки; fakes держать в tests или _test.go. |
| S9 | Структурно | ChangeInfo/AddChange и часть Options API не используются в основном потоке. Получение подробного diff заявлено моделью, но не доведено до потребителя. | Удалить необязательную модель либо добавить только при подтверждённом use case. |
| S10 | Структурно | constancts.go с опечаткой, Gitter/Syncer с расплывчатой семантикой; много очевидных комментариев, но мало описаний инвариантов. | Исправить имена при изменении соответствующего кода; документировать владение root, результат и ошибки. |

Количество пакетов само по себе не проблема. Проблема — произвольные общие interfaces/models/handlers при сильных обратных зависимостях. Для такого размера достаточно нескольких пакетов с понятными владельцами.

### 4.3. Ошибки, HTTP и эксплуатация

| № | Уровень | Наблюдение | Предложение |
|---|---|---|---|
| O1 | Критично | main сообщает об ошибке, но выходит с 0; GitSync.Sync теряет исходную ошибку и всегда возвращает nil. | Ненулевой exit для фатального запуска, явный outcome каждой попытки. |
| O2 | Существенно | hasChanges ставится до успешного Pull/reset. SyncCount может расти после неуспешного обновления. | Разделить detected/published/error/no-op, считать успех после commit-point публикации. |
| O3 | Существенно | storeCurrentCommit ошибки игнорируются, wrapping через %v теряет цепочку causes; nil/type assertion могут вызвать panic. | %w, errors.Is/As, явная валидация, единая классификация ошибок без разборов строки. |
| O4 | Существенно | Context проверяется только между операциями; cancel не отменяет PlainClone/Fetch/Pull. main не ждёт worker; HTTP игнорирует ctx. | Context-aware transport, deadlines, graceful shutdown с ожиданием и ограничением времени. |
| O5 | Существенно | HTTP error приводит к panic в goroutine; нет ReadHeaderTimeout/IdleTimeout и контролируемого bind. | net.Listener + http.Server; ошибка запуска/serve возвращается управляющему коду. |
| O6 | Существенно | Webhook отправляет в очередь до ответа, может заблокироваться; принимает любой метод. HTTP 200 лишь подтверждает enqueue, текст обещает triggered. | POST, 202 Accepted, coalescing одного pending reconcile; результат sync доступен отдельно. |
| O7 | Существенно | Нет schema/verification для webhook конкретного Git-провайдера. Имя webhook может вводить в заблуждение. | Описать ручной trigger endpoint; интеграции GitHub/GitLab добавлять отдельно с их проверкой подписи/токена. |
| O8 | Существенно | Basic частично заполнен → auth может оказаться выключенной; при Basic+Bearer Basic молча имеет приоритет. Корневая страница без auth. | Неполные/конфликтующие настройки отклонять; явно определить доступ к каждому endpoint. |
| O9 | Существенно | TokenAuth — Bearer, не user/token Basic. user игнорируется, Pull без Auth. | Явный auth mode, корректный механизм выбранного Git-сервера, единые credentials для всех операций. |
| O10 | Существенно | Нет readiness/freshness/status; /status в api возвращает пустое поле и не подключён. | Status последних attempt/success/published SHA, degraded отдельно от fatal. Liveness не должна зависеть от доступности Git. |
| O11 | Существенно | Метрики содержат полный URL, email/message/SHA/date. Reset не удаляет старую историю серий в Prometheus. | Ограниченные labels outcome/reason; timestamp/duration значениями, подробности через status. URL очищать от userinfo. |
| O12 | Существенно | Logger singleton лениво создаётся без защиты; методы меняют общий prefix несколькими вызовами. Потокобезопасность log.Logger не делает эти последовательности атомарными. | Стандартный структурированный logger, level в записи; без смены общего prefix. |
| O13 | Существенно | Debug не фильтруется по уровню; Error одновременно логирует и создаёт error, который обычно игнорируется. | Разделить logging и создание errors; однократное сообщение об отказе, selectable verbosity. |
| O14 | Существенно | Нет ограничений retries/stale age, контроля диска, политики восстановления служебных данных после сбоя. | Bounded retry + jitter, last-good snapshot, размер/retention и recovery внутри owned root. |

TLS не обязательно реализовывать внутри сервиса: для sidecar разумно ограничить bind/сеть и использовать существующий ingress/proxy. Но допустимый сетевой периметр и хранение credentials должны быть описаны. Remote URL/ошибки Git не должны раскрывать встроенные секреты.

### 4.4. Конфигурация и доставка

- **Фактический источник имён — constants.** HTTP env в Dockerfile совпадают с constants (GITSYNC_HTTP_AUTH_*), ошибается документация с GITSYNC_HTTP_SERVER_AUTH_*. README также пишет --repo-auth-user/--repo-auth-token, код использует --repo-user/--repo-token; HTTP-флаги README тоже отличаются. Предыдущий план фиксировал рассогласование, но теперь источник ошибки уточнён.
- Viper есть в go.mod, но в прочитанных исходниках чтения config file нет. Обещание файла конфигурации неподтверждено. Для одного repo CLI/env достаточно; не добавлять Viper только ради зависимости.
- Validation пути требует существования, clone рассчитан на создание. os.Stat ошибки, отличные от IsNotExist, и случай «путь — файл» не проверяются надлежащим образом.
- ParseRequestURI не определяет поддерживаемый transport. Нужно валидировать именно контракт сервиса; SSH/SCP-like URL не обещать до поддержки.
- Ошибочный env-duration молча заменяется default; CLI способен его перекрыть, но отсутствие override не должно скрывать ошибку.
- IPv6/hostname/:port отвергаются текущим Split + ParseIP. Поддерживаемые формы определить, разбирать через net.SplitHostPort.
- Docker запекает параметры через ARG → ENV, включая токены, работает root, не содержит политики UID/GID volume. Credentials — runtime secret; поддержка произвольного UID особенно полезна для Kubernetes.
- Toolchain/образ/зависимости требуют отдельного обновления с compatibility checks; по возрасту нельзя утверждать наличие конкретной уязвимости. Viper, daemon и coverage tooling пересмотреть на предмет фактической необходимости.
- Cache CI использует run_id и всегда создаёт новый ключ; восстановление возможно по prefix, но происходит churn. setup-go уже может кешировать зависимости: выбрать один механизм.
- Release содержит старые create-release/upload-release-asset actions; обновить после проверки актуальной поддержки. Job permissions явно не ограничены, checksums отсутствуют, Docker только amd64. Не расширять матрицу без потребности.
- Документацию CLI/env желательно генерировать из общей схемы конфигурации. Две языковые версии и Docker defaults сейчас уже разошлись.

## 5. Качество существующих тестов

| Наблюдение | Что реально проверяется | Что нужно изменить |
|---|---|---|
| Git tests клонируют внешний GitLab и обращаются к invalid-url.com | Сеть + конструктор, с неопределённой доступностью сервера | Локальные fixtures, controlled transport, t.TempDir |
| TestStart: timeout 100 ms, interval 30 s | Контекст завершился; это не доказательство выхода worker или вызова sync | Детерминированный trigger/clock, счётчик вызовов fake, done-channel |
| TestStart затем спит 1 s для «проверки тикера» | Тикер 30 s за это время не срабатывает | Проверять periodic и webhook отдельно, без больших sleeps |
| TestWebhookHandlerFunc закрывает global WebhookCh | Один запуск теста может пройти; повтор в том же процессе способен отправить в закрытый канал | Локальная очередь на экземпляр; тест -count=2 |
| TestValidateFlagsHttpServer создаёт httpServerAddr и другие произвольные имена | Функция ищет http-server-addr, получает пустое значение и возвращает nil | Использовать реальные constants и негативные cases |
| Flags tests меняют logger output, восстанавливают стандартный log через log.SetOutput(nil) | Восстанавливается другой logger, global экземпляр остаётся изменён | Локальный logger/правильный cleanup |
| Metrics test ищет только go_info | Проверяется стандартная runtime-метрика, не бизнес-метрики приложения | Изолированный registry и assertions по outcome/счётчикам |
| Mock.Sync всегда nil, Commit использует time.Now | Не моделируются отказ, slow sync, cancellation и стабильные timestamps | Управляемый fake с заданным Result/error/clock |

Это статические выводы из тестов, не результаты их выполнения. В текущей среде команда обнаружения не нашла Go, поэтому build/test/race/coverage не запускались. Ошибки формата строк на новом toolchain и cross-platform build также нужно проверять реально; не объявлять их подтверждёнными только по чтению.

Приёмка должна быть построена на свойствах продукта:
1. Опубликованный набор файлов соответствует опубликованному SHA.
2. Неуспешная подготовка не меняет last-good.
3. Повторное согласование того же SHA идемпотентно.
4. Target, отличный от default branch, действительно используется.
5. Force-push и одинаковое дерево при новом SHA имеют определённый результат.
6. Сбой сети/диска/auth/публикации корректно отражён и не считается успехом.
7. Подготовка не блокирует HTTP навсегда; SIGTERM завершается за установленный срок.
8. Два writer одного root не работают одновременно.
9. Повторные и конкурентные тесты не зависят от globals.
10. Reader-test проверяет согласованность снимка с учётом контракта чтения.

## 6. Целевая архитектура: небольшой сервис согласования состояния

Предлагаемая структура:

| Каталог | Ответственность |
|---|---|
| cmd/git-sync/ | Сборка объектов, сигналы, exit code |
| internal/config/ | CLI/env, defaults, validation, безопасное отображение |
| internal/syncer/ | Run, Trigger, Status; reconcile одного target; небольшой интерфейс backend рядом с потребителем |
| internal/repository/ | go-git: fetch, resolve SHA, подготовка файлов; без FlagSet/HTTP/Prometheus |
| internal/publish/ | Только при snapshot-режиме: публикация, owned-root lock, recovery, retention |
| internal/httpserver/ | Локальный mux, auth, trigger/status/probes, lifecycle |
| internal/telemetry/ | Registry и перевод Result/Status в метрики |

Logger передаётся как объект стандартного логирования. Универсальные interfaces/models/utils и plugin registry не нужны. Если publish остаётся очень маленьким, держать его внутри syncer до появления самостоятельной логики.

Зависимости: main собирает сервис и adapters; HTTP вызывает Trigger/Status; syncer вызывает repository/publisher; telemetry читает результаты. Git backend ничего не знает об HTTP или метриках.

Предлагаемый внутренний API:
- Repository.Prepare(ctx, target) → PreparedSnapshot + error.
- Publisher.Publish(ctx, snapshot) → PublishedSnapshot + error.
- Service.Run(ctx) → error.
- Service.Trigger(reason) → accepted/coalesced/stopping.
- Service.Status() → копия Status.
- Result различает revisionChanged, contentChanged и published; ошибка возвращается отдельно.

Не создавать интерфейс на каждый тип. Абстракция backend полезна для fakes и возможного сравнения go-git с Git CLI; второй production backend не нужен, пока первый решает требования.

### Состояния и алгоритм

Состояние процесса: initializing → ready; при временной ошибке → degraded с сохранённым last-good; после успешного согласования → ready. Fatal означает невозможность безопасно продолжать. Sync-in-progress — отдельный признак, а не исчезновение ready.

Одна попытка:
1. Проверить владение root и действительность конфигурации.
2. С deadline получить выбранный ref и соответствующие Git objects.
3. Зафиксировать target SHA для этой попытки. Изменение remote во время подготовки увидит следующий reconcile.
4. Если SHA и готовый snapshot уже актуальны — no-op; отдельно отслеживать метаданные при одинаковом TreeHash.
5. Подготовить snapshot вне опубликованного пути.
6. Проверить готовность: полный checkout, необходимые файлы/режимы и поддерживаемые Git features.
7. Переключить published pointer. Это commit-point результата.
8. Обновить status и метрики; затем очистить разрешённые старые данные.

До шага 7 потребитель продолжает читать last-good. Ошибка cleanup после публикации — maintenance error, а не доказательство провала самой публикации. Остановка во время filesystem-операций зависит от их возможностей: context не гарантирует мгновенную отмену каждой локальной операции.

Snapshot root может содержать cache, snapshots/<SHA>, current и служебное состояние. Git objects желательно переиспользовать; первоначально допустим более простой checkout без обещания минимального disk usage. Старые snapshots удалять по retention, сохраняя active и нужные читателям версии.

### Пределы атомарности

Переключение symlink через rename в пределах поддерживаемой файловой системы даёт атомарность указателя, а не транзакцию серии независимых open. Если читатель заново разрешает current для каждого файла, переключение между двумя open может дать смешанные версии. Для согласованного набора читатель должен один раз зафиксировать путь конкретного snapshot и читать все файлы из него.

Также symlink-switch не обеспечивает сам по себе долговечность при power loss. Recovery, fsync и поддерживаемые FS определять по требуемому уровню гарантий. NFS, Windows symlinks, subPath mounts и retention для долгих читателей требуют отдельной проверки; переносимость нельзя объявлять по Linux smoke-test.

## 7. Как сделать приложение эффективнее

Приоритет эффективности — устранить лишнюю работу, затем измерить результат:
- Один fetch на попытку вместо fetch + сетевого fetch внутри Pull.
- Resolve SHA перед дорогостоящим построением diff.
- No-op при неизменном SHA без повторного checkout и полного обхода published snapshot.
- Ограниченный refspec; shallow/single-branch включать после тестирования смены ветки и force-push.
- Контролируемый cache и retention; повторное использование objects вместо полного clone каждой версии.
- Coalescing webhook: сто сигналов означают одну pending проверку актуального состояния, а не сто одинаковых checkout.
- Timeout, backoff с jitter; не допускать плотного опроса при длительной операции. Определить interval как задержку после попытки или фиксированную частоту.
- Контроль числа metrics series, размера repo/cache и периодической очистки.
- Integrity scan опубликованных файлов делать по отдельной политике только если допускаются внешние изменения; readonly mount не исключает запись самого writer, поэтому владение root остаётся обязательным.

Не обещаю процент ускорения без benchmark. Измерять initial sync, no-op, небольшое обновление большого repo, переписанную историю, сетевой отказ и reader concurrency. Снимать duration, CPU, RSS, disk IO, transferred bytes где доступны, размер cache и время восстановления. Сравнивать одинаковый dataset и backend.

## 8. Выбор собственной реализации и альтернатив

Официальный kubernetes/git-sync решает близкую задачу: периодическая/одноразовая загрузка branch/tag/SHA, HTTP(S)/SSH и публикация через worktree + symlink. Он уже выделяет потребительский файловый контракт. Проверен README ветки master на дату анализа; master развивается, поэтому конкретный релиз и его возможности перед внедрением надо закрепить отдельно.

| Вариант | Когда оправдан | Цена |
|---|---|---|
| Сохранить go-git и исправить сервис | Нужен собственный status/API, компактный standalone binary, свои правила эксплуатации | Поддерживать транспорт, snapshots и recovery самостоятельно |
| Git CLI backend | Нужна совместимость с установленным Git, специфическими Git features/credentials | Дополнительный binary, subprocess lifecycle и безопасная передача credentials |
| Использовать kubernetes/git-sync | Требования в основном стандартные: доставка файлов в sidecar/init | Миграция CLI/env/path-контракта, проверка probes/auth/webhook semantics |
| Обёртка над готовым сервисом | Отличия сосредоточены в интеграции/наблюдаемости | Риск дублирования lifecycle; сначала доказать необходимость обёртки |

Рекомендация: перед собственной snapshot-реализацией сделать короткую таблицу обязательных требований и gap analysis с закреплённым релизом kubernetes/git-sync. При отсутствии значимых отличий использовать готовое решение экономически рациональнее. Если свой продукт нужен, заимствовать принцип публикации и контракт, сохранив собственную ограниченную реализацию. Автоматическая замена приложения сейчас не предлагается.

## 9. План развития в логическом порядке

1. **Контракт и baseline.** Уточнить режим файлов, supported transport/features и last-good policy; исправить README; запустить текущие checks в Go-среде.
2. **Тестовый фундамент.** Локальные fixtures, изоляция globals, исправление ложных тестов; fixtures для веток/force-push/dirty.
3. **Корректность операции.** Typed config, единый target SHA/auth, Result/error, initial reconcile и правильные exit codes.
4. **Lifecycle и интерфейсы.** Context/deadline, один worker, неблокирующий trigger, локальный HTTP, status/probes и корректные метрики.
5. **Публикация.** После выбора snapshot-контракта реализовать prepare/publish/last-good/recovery/retention. Для поставки нескольких связанных файлов это ключевое свойство, а не косметический backlog.
6. **Оптимизация по измерениям.** Убрать двойной fetch, ограничить refs/history, проверить no-op и reuse.
7. **Доставка и миграция.** Toolchain/dependencies, non-root container, runtime secrets, volume/restart/upgrade tests; совместимость CLI/env/metrics.

Один функциональный этап — отдельное reviewable изменение с regression tests. Перемещение пакетов выполнять вместе с реальным разделением ответственности, без большого параллельного переписывания. Ветка feature/git-sync-reliability остаётся базой работ; main/develop не изменять этим анализом.

Первые практические изменения безопасно начать с fixtures и передачи errors. Одновременно до реализации публикации нужно выбрать контракт каталога: эта развилка меняет весь алгоритм, пути потребителей и стратегию rollback.
